In a traditional product, a failure state is an error message. In an agentic system, a failure state is an autonomous decision made under bad conditions.

The stakes are categorically different.

## A taxonomy of agentic failures

**Knowledge failures** — The agent acts on outdated, incomplete, or fabricated information. The output looks plausible but is wrong. This is the silent failure: the user may not notice until the consequences arrive.

**Tool failures** — An API call fails, a file is unreadable, a database returns unexpected results. The agent must decide: retry, escalate, or proceed without the tool? Each choice has different risk profiles.

**Scope failures** — The agent interprets its mandate too broadly or too narrowly. It either does too much (takes an action it wasn't authorized for) or too little (stops short of completing the task because it was uncertain about a boundary).

**Ambiguity failures** — The user's instruction was underspecified and the agent chose an interpretation that wasn't what the user intended. This is extremely common and often invisible until the output is delivered.

**Cascade failures** — An early mistake is compounded by subsequent actions taken on the basis of that mistake. In multi-step agentic workflows, errors propagate.

## Designing interrupt points

The highest-leverage design intervention for agentic failure is the interrupt: a designed pause before a consequential, hard-to-reverse action.

Interrupts should be:
- **Proportional** — triggered by actual consequence risk, not reflexive caution
- **Legible** — clearly showing what the agent is about to do and why
- **Actionable** — offering real alternatives, not just a confirm/cancel binary
- **Efficient** — not so frequent that users auto-approve everything

The goal is not to make agents ask permission constantly. It's to reserve human judgment for the moments where human judgment actually matters.

## Recovery design

Recovery from failure should be designed with the same care as the success path. When an agent fails, the user needs to:

1. Understand what happened and why
2. Know the current state (what was completed, what wasn't)
3. Have a clear path to retry, correct, or escalate
4. Trust that the system is being honest about the failure

The failure message is a design surface. Treat it as such.
